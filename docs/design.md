# session-guardian 设计文档（会话效能观察与交接）

> 状态：设计定稿（v1 已实现并安装）。本文件回答「为什么这么做、怎么做、三平台各怎么落地」。
> 配套：`docs/issue-draft.md`（给 deepseek-harness 的 issue 草稿）、`README.md`（安装/使用）。

---

## 1. 一句话

长会话里，模型会「干一点就停、交卷特别早」，而它自己往往看不见自己在衰退。
本项目做一个**会话效能观察者**：在衰退特征出现时（不是靠定时器猜）触发一次「交接」，
把任务状态无损搬到下一个干净会话，从而让**便宜模型也能跑长程任务**。

它由**两个技能**组成：

- `session-observer`（本项目）＝**观察 + 触发**：衰退特征清单、阈值、心跳、一句话诊断。
- `context-handoff`（既有技能，作为依赖复用）＝**交接物**：HANDOFF.md 的格式、判绿脚本、开场指令。

分工边界一句话：**observer 判断「该不该换」，handoff 负责「怎么无损地换」。**

## 2. 三平台能力调研结论（2026-11-12 复核）

> 上一版调研（context-handoff `references/platforms.md`，抓取 2026-10-16）把「豆包 App」写成
> 「一无所获」。**该结论已过时**：豆包 2026-08 起上线「豆包工作」的**技能、定时任务、任务模式（代码运行）**。
> 下表是复核后的结论，标「需实测」的一律不许当事实写进交付物。

| 能力 | DSH（DeepSeek Harness） | Kimi | 豆包 |
|---|---|---|---|
| 技能载体 | `~/.dsh/skills/<name>/SKILL.md`，按需加载 | `~/.kimi-code/skills/`；API 托管智能体有「技能」 | 「豆包工作」有**技能**（有公开技能市场，已有 doubao-cron-scheduler 类技能） |
| **定时器（能否程序化建）** | ✅ `schedule_create`（模型可自建本会话提醒） | ⚠️ 有「定时任务」（产品级）+ API 托管智能体「定时运行智能体（triggers）」，**是否能在对话内程序化建需实测** | ⚠️ 有「定时任务」页（产品级，手动）；**能否程序化建需实测** |
| 现象触发（hook） | ❌ 只有 7 个 hook 事件，无 PreCompact，`transcript_path` 恒空 | ⚠️ 18 事件含 PreCompact，但**返回值被忽略、不能阻断** | ❌ 未证实 |
| 读会话日志 | ✅ 能（本机 zstd 日志，本技能可直接扫） | ⚠️ 需实测 | ❌ 大概率不能（云端） |
| 程序化开新会话 | ❌ 无文档化接口 | ⚠️ 仅 REST/ACP 可 | ❌ |

**三条确定结论**：

1. **三平台都有「技能」载体**，所以「观察协议」作为技能本体，三平台都能装（豆包也不再是空白）。
2. **「定时器」三平台都有，但「模型自己程序化建定时器」只有 DSH 确定能做**；Kimi/豆包是产品级的手动定时任务，能否被模型程序化调用**需要实测**（列为待办，不写进交付物的承诺）。
3. **「读会话日志做确定性判据」只有 DSH 确定能做**（本机日志）。Kimi/豆包是云端，拿不到日志，只能退化为「模型自检」。

**因此三平台落地分两档，这是本项目的地基**：

| 档 | 平台 | 观察方式 | 判断方式 |
|---|---|---|---|
| **硬档** | DSH | 现象→每轮自检 + 定时器心跳 | **确定性脚本扫日志**（数「继续」/压缩次数） |
| **软档** | Kimi / 豆包 | 现象→每轮自检 + 产品级定时任务 | 模型对照特征清单（自觉） |

硬档有脚本兜底、软档靠自觉——这是平台能力决定的天花板，**不假装三平台等价**。

## 3. 项目结构（一组技能，怎么装、怎么用）

```
session-observer/                    # 开源仓库根
├── README.md                        # 安装/使用/三平台说明
├── LICENSE
├── install.sh                       # 一键安装到各平台 skills 目录
├── session-observer/                # 技能本体（平台无关）
│   ├── SKILL.md                     # 观察者本体：触发契约 + 衰退清单 + 动作
│   ├── references/
│   │   ├── degradation.md           # 衰退特征清单 + 阈值 + 判据
│   │   └── platforms.md             # 三平台能力矩阵（本节第 2 章）
│   ├── scripts/
│   │   └── check_session.mjs        # 确定性判据：扫 DSH 会话日志数特征（硬档）
│   └── templates/
│       └── capability-card.md       # 激活时的「能力卡」（阈值可发现性）
├── adapters/
│   ├── dsh/                         # DSH：schedule 心跳 + AGENTS.md 常驻入口
│   ├── kimi/                        # Kimi：skills 路径 + 定时任务说明
│   └── doubao/                      # 豆包：技能安装 + 定时任务说明
└── docs/
    ├── design.md                    # 本文件
    └── issue-draft.md               # deepseek-harness issue 草稿
```

**安装**：`install.sh` 把 `session-observer/` 拷到目标平台的 skills 目录（DSH `~/.dsh/skills/`、
Kimi `~/.kimi-code/skills/` 或 `~/.agents/skills/`、豆包按「豆包工作」的技能安装方式），
并把 `context-handoff` 作为依赖一起装（或声明已装）。

**使用**（三条入口，跨平台一致）：
1. **自动**：DSH 上靠 `~/.dsh/AGENTS.md` 常驻入口（每会话自动带上观察协议）。
2. **一句话建观察**：任何会话里说「**观察**」→ 立即启用观察 + 分析当前会话是否该换。
3. **一句话诊断**：说「**观察**」（同上）或「**该换会话吗**」→ 扫当前状态 → 出切换建议 + 开场指令。

### 唤醒机制（为什么「常驻入口」是默认动作）

技能是**按需加载**的，不是每会话自动加载。只装技能、不加常驻入口时，「观察」只在用户主动说、或模型恰好想起自检时发生——唤醒是随机的。

所以唤醒分三层，逐层提高「任何情况正确唤醒」的几率：

| 层 | 机制 | 触发 | 覆盖率 |
|---|---|---|---|
| ① 常驻入口 | `~/.dsh/AGENTS.md` 追加一段观察协议 | 每会话自动带上 | 100%（DSH） |
| ② 主动一句话 | 用户说「观察」/「该换会话吗」 | 用户明示 | 按需 |
| ③ 现象自检 | 模型每轮对照衰退清单 | 衰退特征出现 | 依赖 ① 被唤醒 |

**常驻入口（①）是默认动作的原因**：它是唯一不依赖「用户想起」或「模型想起」的唤醒路径。没有 ①，②③ 都悬空——用户可能不知道能说「观察」，衰退中的模型更不会主动自检。所以安装后**默认追加 AGENTS.md 入口**，而不是「可选」。

代价：AGENTS.md 常驻占一点上下文。所以只放「入口」这一段（轻），完整判据在技能本体里（按需加载）。

## 4. 交接物时效校验（Q4 兜底节点）

**问题**（用户实测）：模型读到一份 `HANDOFF.md` 说「已过期 3 天」，却差点照它的 `status.下一步` 执行。

**根因**：`HANDOFF.md` 是**快照**，不是活状态。会话在交接之后又跑了 3 天，快照就过期了。

**设计原则**：**交接物不是交接的起点，而是交接的产物。** 真正切换前，必须从「当前真实状态」重新生成一次，永不复用旧文件。

**兜底节点＝「落地前重生成」，放在触发→动作的最后一步**：

```
触发（衰退/阶段完成/用户说交接）
  → ① 重新采集当前真实状态，不读旧 HANDOFF：
         · git rev-parse HEAD（当前基线）
         · 最近 N 轮实际做了什么（会话日志/文件 mtime）
  → ② 生成/刷新 HANDOFF：updated_utc=now，恢复检查点=当前 HEAD
  → ③ check_handoff.mjs check 判绿
  → ④ 才提议切换 + 给开场指令
```

**「过期检测」是反向的**：不靠"判断旧文件过没过期"（那是猜），而是**一律当旧文件未验证**，用当前状态重新生成。这直接消除"3 天前的快照被当最新"这一整类风险。

**恢复侧**（新会话刚开，读 HANDOFF 时）再加一道：`updated_utc` 与 `恢复检查点` 必须与新会话自己跑的 `git rev-parse HEAD` 一致；不一致就以实测为准、先纠正再干（context-handoff 的"五问"第 5 问已在做，这里显式点名）。

## 5. 阈值可发现性（Q5）

**问题**：用户怎么知道可以说「阈值：连续 2 次就提示」？

**方案（参考主流技能/CLI 的三板斧）**：激活即宣告 + 帮助词 + 首次询问。

1. **激活时自报「能力卡」**（主发现机制）：observer 每次启用，输出一张紧凑能力卡，其中明确列「阈值可改」：
   ```
   【会话观察已启用】
   · 衰退判据：连续≥3次「继续」/ 一件就交卷 / 压缩后失忆 / 重复不升级 / 约束漂移
   · 阈值可改：说「阈值：连续2次」即改（本会话生效）
   · 一句话诊断：说「观察」立即分析本会话是否该换
   · 帮助：说「观察帮助」查看全部命令
   ```
2. **帮助触发词**：「观察帮助」→ 输出全部可配置项 + 当前值。
3. **首次运行问一次**：阈值默认 3，首次激活时问「用默认 3 吗？可随时说『阈值：N』改」——把"可配置"这件事在一开始就点破。

**阈值存哪**：协议里一行 `threshold: 连续3次继续`，可被「阈值：N」覆盖。**跨平台统一走"文本行"，不依赖配置文件**（豆包云端读不到本地文件）。

## 6. 三平台定时器接入（Q3 结论）

| 平台 | 机制 | 谁建 | 状态 |
|---|---|---|---|
| DSH | `schedule_create`（周期提醒） | 模型自建 | ✅ 确定可行 |
| Kimi | 产品「定时任务」/ API 托管智能体「triggers」 | 用户手动，或 API 建 | ⚠️ 程序化建需实测 |
| 豆包 | 产品「定时任务」页 | 用户手动 | ⚠️ 程序化建需实测 |

**兜底统一方案（三平台都能走）**：定时器只是**保险丝**，不是主触发。主触发是「现象→每轮自检」——
技能让模型每轮对照衰退清单，用户第 3 次打「继续」这个现象本身就是触发信号，零定时器、零平台差异。
定时器只在"模型退化到连自检都不做"时兜底。所以三平台**即使定时器机制不同，观察能力都成立**。

## 7. 未证实清单（交付物里必须标"需实测"，不许当事实）

- Kimi：对话内能否由模型程序化建定时任务；能否读本机会话日志。
- 豆包：技能的具体安装路径与自动加载机制；「定时任务」能否被程序化调用；能否读会话日志。
- 三平台通用的「程序化开新会话」：一律按「给命令/给可粘贴指令」降级，不声称自动跳转。
