## 上下文交接（context-handoff）常驻规则

本机装有 `context-handoff` 技能。**不要等上下文满了才开始交接。**

**最优时机是"一个交付单元刚完成"，不是"上下文快满了"。** 顺序别做反：

### ① 首选：交付单元完成时 → 做**阶段交接**并**换会话**

"交付单元"＝**三条同时满足**：有可判真假的验收 ／ 不依赖未完成的半成品 ／ 已落盘。
（典型：一个独立功能的设计＋实现、一个 bug 的定位＋修复、一个模块重构、一次数据迁移。）

- 此刻你对"刚做了什么"最清楚 ⇒ 交接物失真最小、接续方几乎不用猜。
- **别在单元中途换会话**：那样必然带半成品，续接方要先猜你做到哪，比不换更差。
  中途只做下面的"检查点"。
- 单元也别太小（一步一换，切换开销 > 收益）。

### ①-b 动手前先探一句（不要替用户决定）

在**准备开始下一步之前**，问自己一句：

> 「我接下来要做的事，是不是和刚做完的是同一个交付单元？」

- **是** ⇒ 继续做，顺手刷个检查点。
- **不是** ⇒ 先做阶段交接并判绿，然后**向用户报告**：

```
【交接建议】当前交付单元已完成：
· 验收：<命令/判据> 已通过
· 交接物：./HANDOFF.md 已判绿（round N）
· 下一步「X」属于新的交付单元，建议在这里换会话。
（你若想继续在这个会话里做，说一声"继续"就行——我不会阻塞。）
```

三条硬约束：**不自动中止**（你结束不了会话，只能停下并交回决定权，别写成"已切换"）、
**不阻塞**（用户说继续就照常做，不重复唠叨）、**不以占用率高低为理由**提出换会话（依据是单元边界）。

### ② 常规：检查点（防中断，成本约 0.2 秒，可以很勤）

1. 一个可验证的步骤刚完成（测试转绿 / 文件落盘 / 命令跑通）；
2. `HANDOFF.md` 里的「下一步」或「禁止」变了；
3. 你准备进入一段**长耗时**操作（大重构、批量测试、长命令）——**动手之前先写**；
4. 你发现自己**在重复同一种手段**（连续 2 次失败还没换思路）——停下来，交接，别换皮重试。

### ③ 预警与应急

5. 用户提到"交接""换会话""总结进度给下一个会话"；
6. 平台提示上下文即将压缩，或刚刚压缩过（**到这一步已经是"不得不"，不是最优**——
   此时模型已进入长上下文退化区，交接质量会下降）。

**交接怎么做（必须遵守）**：

- 产物是工作区根目录的 `HANDOFF.md`；首次用 `init` 建骨架，之后一律**增量**更新。
- 增量更新用 `next`，只声明**真正变化**的节（1–2 个），未变节由工具逐字搬运。
- 落盘前必须判绿：
  `node "<技能目录>/scripts/check_handoff.mjs" check ./HANDOFF.md`
  退出码 `0`=绿、`2`=判红（字段缺失/空面）、`3`=用法错。**红就不许往下走。**
- `provenance.trigger` 如实记录触发来源（`checkpoint`/`context-pressure`/`pre-compact`/
  `post-compact`/`degradation`/`interruption`/`error-recovery`/`compaction-failed`/
  `round-limit`/`budget-quota`/`user-request`/`phase-complete`/`peer-request`/
  `device-switch`/`model-switch`/`self-estimate`）。**不许用 `self-estimate` 冒充外部阈值。**

**压缩之后必须重建落地**：把交接物里的"已完成"逐条当**未验证**，用实测核对；
不要因为摘要里写着完成就跳过。

**能力边界（不许对外承诺"无损"）**：上一个检查点之前的工作可无损接续；
检查点之后到中断之间的工作**可能丢失**。
