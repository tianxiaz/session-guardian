# 上下文交接（context-handoff）

**这份文件是平台无关的本体。** 它不假设任何平台的钩子、命令或工具名。平台差异一律在 `adapters/`，
本文件在**任何**支持 Markdown 技能的平台上都**逐字相同**（平台清单与能力差异见 `references/platforms.md`）。

---

## 0. 一句话

上下文压缩必然丢信息。所以不要靠"模型记住了多少"，而是把**接续必需的事实**搬进一个
**有固定字段、可被脚本判红、可幂等更新**的文件：`HANDOFF.md`。新会话只读它就能继续干活。

---

## 1. 触发契约（谁在什么时候调用本技能）

触发**不只"上下文快满了"这一种**。共有三条失效轴，而对它们的对策**根本不同**：

| 轴 | 怎么失效 | 会话还活着吗 | 模型还能写吗 | 对策 |
|---|---|---|---|---|
| **A 信息失真** | 上下文被压缩/填满，早期决定失真 | 能 | 能 | **到点交接** |
| **B 执行中断** | 会话/请求/进程被外部终止（假死、被杀、超时、限流、崩溃、压缩自己失败） | **不能** | **不能** | **只能提前写**：写前式检查点 |
| **C 主动边界** | 没出错，只是到了自然交接点 | 能 | 能 | 到点交接 |

**B 轴是最危险的一条**：它发生时你已经没有机会写任何东西了。所以对 B 轴，
"到阈值再交接"这条路不存在——唯一防线是**趁还活着就写新**（见 §1.2）。

### 1.1 触发词（`provenance.trigger`，17 个取值，判据会校验）

| 轴 | 取值 |
|---|---|
| A | `context-pressure`（旧别名 `external-threshold`）、`pre-compact`、`post-compact`、`degradation`、`model-switch` |
| B | `interruption`、`error-recovery`、`compaction-failed`、`round-limit`、`budget-quota` |
| C | `user-request`、`phase-complete`、`checkpoint`、`peer-request`、`device-switch` |
| 兜底 | `self-estimate`（**必须如实标注**；伪装成外部阈值会被判红） |

**必填**：`trigger`。**可选归因**：`trigger_detail`，写平台侧的具体信号名（如 `rate_limit`），
用于事后归因，不参与判绿；写了就不许留空。

**触发优先级（从"最优"到"最次"）**——这条比取词表更重要：

| 优先级 | 时机 | 为什么排这里 |
|---|---|---|
| **① 首选** | **`phase-complete`：一个交付单元刚完成** | 此刻你对"自己刚做了什么"最清楚，写出来的交接物**失真最小**；换会话也最干净 |
| ② 常规 | `checkpoint`：例行轻量刷新 | 防中断用，成本极低（约 170 ms），可以很勤 |
| ③ 预警 | `context-pressure` / `pre-compact` | 到这时模型已进入**长上下文退化区**，交接质量开始下降——是"不得不"，不是"最好" |
| ④ 应急 | B 轴（`interruption`/`error-recovery`/`compaction-failed`/…） | 已经出事了，只能靠之前的检查点救 |

> **别把顺序做反。** 阈值触发看起来"有量化依据所以更科学"，但它落在模型状态**最差**的时刻；
> 而交付单元边界落在模型状态**最好**的时刻。同样的判据脚本，交接物的实际质量差很多：
> 单元边界写的交接物，接续方几乎不用猜；阈值触发写的，常带着半成品和模糊的"下一步"。

**每个触发词该怎么动作** → `references/triggers.md §6` 有逐条表。这里只列三个最容易做错的：

- `post-compact`：**重建落地**，不是继续干。重读交接物、重跑验证命令；
  把压缩摘要里的"已完成"当**未验证**（有平台已实测记录过这个失效模式，见 `references/triggers.md`）。
- `degradation`：**熔断**。同一手段连续失败 2 次就停下写交接（把"试过什么、为什么不行"
  写进 `decisions.尝试过`），不要继续换皮重试。
- `interruption`：重开后的**第一件事**。先核对 `status.恢复检查点` 与仓库实测，再干别的。

### 1.2 交接时机：**单元边界优先，检查点兜底**

这里有两种不同粒度的动作，别混用：

| | **阶段交接**（首选） | **检查点**（兜底） |
|---|---|---|
| 何时 | 一个**交付单元**刚完成 | 任一"该刷一下"的信号（见下） |
| 粒度 | 单元级（一个功能／一个 bug／一次重构） | 步级，可以很细 |
| 成本 | 完整走 §4（含更新 `evidence`、写清下一阶段入口） | 只改 1–2 个节，约 170 ms |
| 目的 | **换会话**，让下一段在干净上下文里开始 | **防中断**，把已做的落盘 |
| `trigger` | `phase-complete` | `checkpoint` |

#### 什么是"一个交付单元"（三条同时满足才算）

1. **有可判真假的验收**——能写出"怎么算完成"（测试转绿／命令输出符合预期／文档落盘）；
2. **不依赖未完成的半成品**——别人接手时不需要先猜你做到哪；
3. **已落盘**——代码已写、已跑过、已（或明确决定不）提交。

典型单元：一个独立功能的设计＋实现、一个 bug 的定位＋修复、一个模块的重构、一次数据迁移。
**不是**单元：单个文件改完、单条命令跑通、单个测试变绿（那些是检查点的触发，不是换会话的时机）。

#### 为什么单元边界最优（这是有机制的理由，不是风格偏好）

- **交接物的质量，取决于写它的那一刻你对自己刚做的事有多清楚。** 单元刚完成时，相关事实都在近期上下文里、
  且没有半成品噪音 ⇒ 写得最准。
- **阈值触发的交接，恰好发生在模型状态最差的时候。** 长上下文填充后会出现重复循环、不升级、
  指令漂移、盲信压缩摘要等退化（有平台已实测记录，见 `references/triggers.md §3`）。
  也就是说：**最需要高质量交接的时刻，写出来的东西质量最差。**
- **单元中途交接天然带半成品**：接续方要先猜"你做到哪一步"，"下一步"也碎。单元边界没有这个问题。

#### 单元不能太大也不能太小

| 单元太小（一步一换会话） | 单元太大（跨多个单元才交接） |
|---|---|
| 切换开销 > 收益：新会话要重读交接物、重跑验证 | 上下文利用率高但**交接质量下降**，且单元间状态纠缠，"下一步"变模糊 |

**恰当大小＝一个可独立验收的交付单元**（例如"项目中的一个独立大功能设计开发"）。
这是**经验上的甜点区**，不是定律——按你的任务实际调整。

#### 什么时候刷检查点（满足任一）

1. 一个**可验证**的步骤刚完成（测试转绿／文件落盘／命令跑通）；
2. `boundaries.禁止` 或 `status.下一步` 变了；
3. 距上次检查点已过若干轮（建议 5–10 轮）；
4. **准备进入一段长耗时操作之前**（大重构、批量测试、长命令）——动手前先写；
5. 你怀疑自己开始"重复同一手段"——立即写。

检查点**很便宜**：只声明变化的那 1–2 个节，其余由工具逐字搬运（见 §2）。
判据与完整交接**完全相同**（`check` 必须判绿）——区别只在粒度与频率，不在质量。

> ⚠️ **反模式：不要在交付单元**中途**做"完整阶段交接"并换会话。**
> 那时必然带半成品状态，续接方要花力气重建你的进度，效果比不换还差。
> 中途只做**轻量检查点**（防中断），等单元完成再做阶段交接。

#### 下一单元探测：**动作之前**问一句，**提议**而不是替他决定

单元边界不靠"我感觉做完了"，而靠一个**更锐利的问题**：

> **"我接下来要做的事，是不是和刚做完的是同一个交付单元？"**

- **是** ⇒ 继续（顺手刷个检查点）。
- **不是** ⇒ 这是一个边界：**先做阶段交接（判绿），再向你的人类报告并让他决定是否换会话。**

**判别参考**（不要凭感觉，逐条对）：

| 信号 | 同一单元 | 新的单元 |
|---|---|---|
| 验收标准 | 同一条验收命令／同一个"算完成"的定义 | 需要新的验收标准 |
| 改动面 | 还是那批文件／那个模块 | 主要动**新的**文件／模块 |
| 依赖关系 | 要用到当前单元**内部**还在变的结构 | 只依赖当前单元**已经稳定的产出** |
| 交付状态 | 做完这一步当前单元**仍不可独立交付** | 当前单元做完就可独立验收 |

**探测时机：动作之前，不是之后。** 等你已经开始新单元再问，上下文已经被污染了。

**报告模板（提议，非阻塞）**：

```
【交接建议】当前交付单元已完成：
· 验收：<哪条命令/判据> 已通过（见 HANDOFF.md 的 evidence）
· 交接物：./HANDOFF.md 已判绿（round N）
· 下一步「<X>」判断为**新的交付单元**，与刚完成的不是同一件事。

建议在这里换会话（干净上下文），续接方式见本平台适配层（adapters/<平台>/README.md）。
如果你更想在同一会话里continue，也完全可以——告诉我"继续"即可，我不做任何阻塞。
```

**三条硬约束（少一条就变成坏设计）**：

1. **不许自动中止**。Agent 无法自己结束会话；能做的是"停止推进 + 把决定权交回人"。
   把"提议"写成"已中止/已切换"就是**声称未做之事**。
2. **不许阻塞**。人可能就想一口气做完三件事。提议被无视后**照常继续**，不重复唠叨。
3. **不许以"我猜你快满了"为理由提议**。提议的依据必须是**单元边界**，不是占用率
   （占用率低时也可能该换——比如一个单元刚收尾；高时也可能不该换——比如只差最后一步）。

> **为什么把决定权交给人**：边界判断天然模糊，而你（人）有 Agent 看不到的信息——
> 项目节奏、deadline、你自己的精力、接下来是不是要开会。**Agent 提议、人决策**，
> 比"Agent 自动切"安全，也比"等人自己想起来"可靠。
>
> **顺带一个给人用的习惯**：换话题前先说一句「交接」。这一句就是 `user-request` 触发，
> 比任何自动探测都准——因为你最清楚节奏。

> ⚠️ **能力边界，别含糊成"无损"**：本技能能承诺的是——
> **上一个检查点之前的工作可无损接续；检查点之后到中断之间的工作可能丢失。**
> 检查点越勤，可丢窗口越小。B 轴里的「假死／被 kill／超时／崩溃」在模型侧**不可观测**，
> 所以谁也不能承诺"一定接得上"。

### 1.3 量化取值（有就拿，没有就如实说）

若平台提供量化值：读 `adapters/<平台>/README.md` 里给出的取数命令，把数字写进
`provenance.occupancy`（0–1 的小数或 `unavailable`）与 `provenance.occupancy_source`
（形如 `<平台>:<测量源>`）。**取不到就不要编**，写 `unavailable`。

> ⚠️ **占用值可能偏低，不得作为唯一触发依据。** 平台报的样本可能取自较早时刻（压缩刚发生、
> 切换模型、同工作区有更新的会话时尤为明显），而**偏低方向的错误最危险——该交接时不交接**。
> 所以 `occupancy` 只作**预警**；关键节点请按 §1.1 的 C 轴（用户明示／阶段收尾）或 §1.2 检查点主动交接，
> 不要等阈值。`measure` 的 `--json` 输出带 `stale` 与 `sampledAtSeq` 供核对。

## 2. 两态状态机（首轮 / 后续）

```
                 ┌─ 无 HANDOFF.md ─────────────► S1 建立（init）
调用本技能 ──────┤
                 └─ 有 HANDOFF.md ────────────► 先 check；绿则 S2 增量更新（next）
                                                红（空面/缺字段/漂移）则先修红再 S2
```

- **S1 建立**：`init` 产出骨架 → 你逐节填真内容 → `check` 必须绿。
- **S2 增量更新**：**不是重写全文**。只改真正变化的节；未变节必须**逐字保留**原字节。
  做法：用 `compare` 找出变化节 → 只重写这些节的内容 → 用 `next` 生成新文件（工具会把未变节原样搬过去）。

**`--payload` 的完整形状**（这是唯一需要手写的输入，务必按此写；形状错会被判成 exit 3 并点名缺哪节）：

```json
{
  "changed": ["status", "todo"],
  "sections": {
    "status": "- 已完成：…\n- 进行中：…\n- 阻塞：无\n- 待办：①做 A\n- 下一步：<一条能立刻敲的命令>\n- 验证：<真跑过的命令>\n- 恢复检查点：HEAD=<哈希>（工作树是否干净）",
    "todo": "- 待办：①做 A"
  },
  "updated_utc": "20261016T1710Z"
}
```

- `changed`：**只列真正变化的节**；未列的节由工具从上一版**逐字搬运**。
- `sections`：`changed` 里每个节 id 都必须在这里给出**该节的完整新节体**（不含哨兵注释）。
- 改 `status.待办` 时通常要同时声明 `todo`（两处必须逐字节一致）。
- `updated_utc` 可选；不给你就得自己在正文里说明时间（工具为保幂等不会替你填当前时刻）。

**为什么两态必须分开**：每次触发都重写全文 ⇒ 表述漂移、细节丢失、历史被抹平。
`next` 子命令的存在就是为了让"未变项逐字保留"成为**结构性事实**，而不是一句承诺。

**粒度事实（用之前必须知道）**：声明式合并的最小单位是**节**，没有补丁级粒度 ——
- 若两个节必须协同改（例如改了 `status.待办` 就要同步 `todo.待办`），**可同时声明多个节**：
  `"changed": ["status","todo"]`，工具会一次替换这两节，其余节仍逐字搬运。
- 只想改**一个标点**也必须**整节重写**并声明该节 —— 这不是 bug，是"未变项逐字保留"的代价。
  别为了小改动去绕过 `next` 手改文件，那会让"未声明变化"的机械复核失去意义。

**幂等判据**：同样的输入连跑两次，第二次产出的文件与第一次**逐字节相同**。
若 `check --against` 报出"未声明变更"或"声明了变更但无差异"，即判红。

## 3. 落盘位置（按优先级取第一个可用者）

1. 若当前工作区存在 `handoff/` 目录：`handoff/HANDOFF.md`，归档进 `handoff/archive/`。
2. 否则若存在 `docs/` 目录：`docs/HANDOFF.md`，归档进 `docs/handoff-archive/`。
3. 否则当前工作区根：`./HANDOFF.md`，归档进 `./.handoff-archive/`。

**归档有两处，别混淆**：
- **增量归档**（`next --archive-dir <目录>`）：把"更新前那一版"留档，位置由你指定；
- **回退留档**（`restore` 自动做）：把"被回退掉的那一份"留档到目标同目录的 `.handoff-archive/`。
两者都只追加、都内容寻址命名，**永不修改**。

**归档是只追加的**：每次更新都把**更新前**的那份**逐字复制**进归档目录。
归档名是**内容寻址**的 `round-<轮次>@<节指纹>.md`（**不是时间戳** —— 时间戳会让「同一状态重放」
产出新文件名，自己破坏幂等）。这件事**由工具做**：`next --archive-dir <目录>`。
归档文件**永不修改**，它是"当时以为什么"的唯一凭据。

**并发保护**：写之前先看目标文件 mtime；若在你读完与写回之间被改过（mtime 变新），
**不覆盖**，改为写入 `<目标>.conflict-<时间戳>.md` 并停下来报告冲突。绝不静默吞并他人在建内容。

**原子写**：先写同目录临时文件，再 `rename` 覆盖。禁止"直接截断再写"。

## 4. 执行步骤（严格按序）

### 4.1 先量后写
1. 定位或创建 `HANDOFF.md` 路径（§3）。
2. 取量化占用（§1 末段）；取不到就留空并注明 `unavailable`。
3. `node <本技能目录>/scripts/check_handoff.mjs check <路径>`：
   - 退出码：`0`＝绿；**`2`＝判红**（字段缺失/空面/漂移）；**`3`＝用法或前提错误**（文件不存在、未知参数、目标已存在未加 `--force`）。
     **2 与 3 都要先处理**；但 `3` 通常是命令写错了，别误当成「交接物不合格」。
4. `node <本技能目录>/scripts/check_handoff.mjs compare <旧> <新>`（仅 S2）：得到变化节清单与逐节差异。

### 4.2 收集事实（不许凭记忆）
每条要写进交接物的事实，**必须有一条可复核来源**：

- 文件/代码：写**相对路径**，必要时附 `:行号`（引用行号前**回读原文**确认）。
- 命令结果：写**真实跑过的命令**与其**真实输出摘要**（含实测数字）。
- 提交：写**真实哈希**（`git log --oneline -1` 的输出，别手写）。
- 决议：写**为什么**（否则新会话会推翻它）＋**被否掉的反方案及原因**。

**没有来源的事实不写。** 宁可写"未验证"，也不许写看起来合理的猜测。

### 4.3 写产物
按 §5 的固定字段写。字段名与顺序**不可改**（脚本按名字校验）。

### 4.4 判绿
```
node <技能目录>/scripts/check_handoff.mjs check <路径>            # 必须 exit 0
node <技能目录>/scripts/check_handoff.mjs compare <旧> <新>       # S2 必须 exit 0
node <技能目录>/scripts/check_handoff.mjs next <旧> --payload <p.json> --archive-dir <归档目录>
```
`check` 红 ⇒ 不许宣布交接完成，不许产出开场指令。

**退出码（完整表，别只看 0/2）**：
`0` 绿 ｜ `2` 判红 ｜ `3` 用法/前提错误（含未知参数、目标已存在未加 `--force`）｜
`4` 并发冲突（`--expect-mtime` 不符，或锁文件被占）。
**未知 `--flag` 一律 exit 3** —— 拼错的保护参数（例如 `--expect-mtme`）不会被静默忽略。

**归档必须由工具做**：`next --archive-dir <dir>` 把**更新前**那一版逐字写到
`<dir>/round-<轮次>@<指纹>.md`（内容寻址 ⇒ 同一状态重放不新增归档，也不破坏幂等）。
**不要手工造带时间戳的归档名** —— 那等于自己破坏幂等。`restore <归档> <目标>` 可回退，
且回退前会把「当前这份」也留档。

### 4.5 产出开场指令
用 `templates/OPENING_PROMPT.md` 生成一份**可直接粘贴**的开场指令，
放在交接物同目录的 `OPENING_PROMPT.md`。里面只写三件事：
① 读哪个文件（绝对或相对路径）② 按哪一节执行下一步 ③ 本项目的铁律一句话。

### 4.6 升级或降级（自动开新会话）
按平台能力取**最高可用档**，并在报告里写明用了哪一档：

| 档 | 条件 | 动作 |
|---|---|---|
| A | 平台支持以程序方式创建会话 | 自动开新会话，把开场指令作为首条消息送入 |
| B | 平台支持命令行续接/新建 | 给用户**一条可复制命令** |
| C | 都不支持 | 给**可粘贴开场指令**（`OPENING_PROMPT.md` 的内容） |

**降级不是失败**：档 C 是「平台没有程序化开会话能力」时的正常形态，不是缺陷。但**不许把 A 说成已实现**。

### 4.7 报告
给用户一段**可核验**的收尾报告，必须含：交接物路径｜归档路径｜变化节清单｜
`check` 与 `compare` 的真实退出码｜触发器类型与占用值（或 `unavailable`）｜升级档位｜**仍未完成项**。

## 5. 产物规范（固定字段，脚本按名校验）

### 5.1 节标记（不可省略）

每个节必须被一对哨兵包住，**节名与顺序固定**：

```
<!-- handoff:section id=goal -->      … <!-- /handoff:section -->
<!-- handoff:section id=status -->    … <!-- /handoff:section -->
<!-- handoff:section id=decisions --> … <!-- /handoff:section -->
<!-- handoff:section id=todo -->      … <!-- /handoff:section -->
<!-- handoff:section id=boundaries -->… <!-- /handoff:section -->
<!-- handoff:section id=environment -->… <!-- /handoff:section -->
<!-- handoff:section id=evidence -->  … <!-- /handoff:section -->
<!-- handoff:section id=open_questions -->… <!-- /handoff:section -->
```

文件开头（第一个节之前）必须有 `provenance` 区块：

```
<!-- handoff:provenance -->
version: 1
round: 1
updated_utc: 20261016T1530Z
workspace: /abs/path/to/workspace
trigger: user-request          # 取值见 §1.1 表与下方说明（别照抄竖线枚举）
occupancy: 0.83
occupancy_source: <平台>:<测量源>
supersedes: round-2@a1b2c3d4e5f6
status: draft                  # draft | complete | blocked
<!-- /handoff:provenance -->
```

`trigger` 的合法取值以 **§1.1 的表**为准（A/B/C 三轴共 17 个），示例里只能填其中一个。
**别把竖线枚举整行抄进去** —— 那会被当成一个非法值并判红（`E_PROVENANCE_TRIGGER`）。
**别把竖线枚举整行抄进去** —— 那会被当成一个非法值并判红（`E_PROVENANCE_TRIGGER`）。
`version`/`round`/`updated_utc`/`workspace`/`trigger`/`status` **六项必填**；
`occupancy`/`occupancy_source`/`supersedes` 允许写 `unavailable` 或留空（首轮 `supersedes: none`）。

### 5.2 各节必含子项

| 节 id | 必含子项 | 要求 |
|---|---|---|
| `goal` | `目标`、`验收` | 验收必须是**可判真假**的句子，不是"做好了" |
| `status` | `已完成`、`进行中`、`阻塞`、`待办`、`下一步`、`验证`、`恢复检查点` | **全部必须有内容**：确无则写 `无`；**`下一步`必须是一条可立即执行的命令或动作**；`恢复检查点` 写真实 commit 哈希＋工作树是否干净（第 5 问靠它回答） |
| `decisions` | `决定`、`理由`、`已否决`、`尝试过` | 每条决定必须带理由；`已否决`写被否方案＋原因；**`尝试过`写试过什么、为什么不行**——这是防"新会话重走死路"的唯一防线 |
| `todo` | `待办` | 与 `status.待办` **逐字节必须相同**（脚本比对，不一致判红）。**做法：先写 `status.待办`，再把同一段文本原样贴进 `todo`**。**我们故意不做自动镜像** —— 镜像会让判据永远绿、失去「有人手改一处忘了另一处」的探测能力；这个取舍是有意的，别把它「优化」掉 |
| `boundaries` | `可改`、`禁止`、`归属未定` | `禁止` 至少一条且要**具体到文件/操作**；没有禁区本身就是危险信号 |
| `environment` | `路径`、`服务`、`命令`、`依赖状态` | `命令` 必须是**真跑过**的验证命令，且要**带工作目录**（写 `cd <绝对路径> && <命令>`，别只写 `$PWD` —— 那会绑到"写它时的目录"）；`依赖状态` 写外部依赖现在能不能用 |
| `evidence` | `提交`、`文件`、`实测数字` | 每项带路径/哈希/数字；无则写 `无` |
| `open_questions` | `待裁决` | 需人来定的问题；无则写 `无` |

> ⚠️ 上表是**判据的真源**。`templates/HANDOFF.md` 是**生成物**（由 `scripts/gen_template.mjs`
> 从 `scripts/lib/handoff.mjs` 的 `REQUIRED_ITEMS` 生成），**不要手改模板** —— 两者漂移时
> 自测里的"模板一致性"用例会判红。

### 5.2.1 验收标准是"五问"（不止四问）

新会话**仅凭 `HANDOFF.md`** 必须能答出：

1. **目标与验收**是什么？ → `goal.目标` + `goal.验收`
2. **下一步**做什么？ → `status.下一步`（必须是一条能立刻敲的命令或动作）
3. 哪些东西**不能碰**？ → `boundaries.禁止`
4. 用什么**命令验证**？ → `environment.命令`
5. **这份交接物描述的基线，与当前仓库一致吗**？ → `status.恢复检查点` 里的 commit 哈希
   与新会话自己跑的 `git rev-parse HEAD` 比对（**这一问是给"工作树已漂移"准备的**：
   前四问都能答、但基线过期时，新会话仍会照着一份过期的状态干活）

任一条答不出 ⇒ **交接不算无损**。`check` 会机械兜底前四问对应字段的完整性，
但第 5 问需要新会话实际比对 —— 所以它写进了必含子项。

### 5.3 写"空面"是错的

"这一节没内容" **不是**可以留空或静默省略的理由：

- 确定没有内容 → 写 `无`（显式否定，可判真假）。**不要写 `—` 或 `-`** —— 那等于没写，会判红
- 不确定有没有 → 写 `未复核` 并说明复核方法
- **留空 / 只在心中省略 / 编一句看起来合理的** → 三者都是错的，前者 `check` 判红，后者是造假

## 6.1 术语速查（三个自造词，一次讲清）

| 词 | 就是什么 | 出现在哪 |
|---|---|---|
| **交接头（`provenance`）** | 文件开头那段键值对：版本、轮次、时间、工作区、触发器、占用量、继承了哪一版、状态 | `<!-- handoff:provenance -->` 区块 |
| **节标记（哨兵）** | 包住每一节的一对 HTML 注释 `<!-- handoff:section id=xxx -->` … `<!-- /handoff:section -->`。**必须逐字保留**，因为合并靠它按字节切片 | 每节首尾各一行 |
| **声明式合并** | 只重写你在 `payload.changed` 里**声明**的那几节，其余节从上一版**逐字搬运**；没声明却变了会被判红 | `next` 子命令 |

另外两个词：**骨架**＝`init` 产出的未填写模板；**`<!-- HANDOFF:CONTENT -->`**＝"这一节还没填"的标记，
填完就删掉该行。

## 7. 自检清单（每轮交接结束前逐条对）

1. `check` 退出码是 `0` 吗？（不是就别报完成）
2. `status.下一步` 是不是一条别人能立刻敲的命令？
3. `boundaries.禁止` 写了吗？有没有把"别人的在建文件"写进去？
4. `todo` 与 `status.待办` 逐字节一致吗？
5. 每条事实都有来源吗？有没有"我猜"混在里面？
6. 触发器类型如实写了吗？自估有没有伪装成外部阈值？
7. 归档真的写了吗（把更新前那份逐字复制过去）？
8. 仍未完成项，我在收尾报告里逐条列了吗？
9. **这是不是一次"检查点"？**（§1.2）如果是，我有没有把成本压到"只改变化的 1–2 个节"？
10. **`trigger` 写的是真实来源吗？** 是 B 轴（中断/限流/压缩失败）就别写成 `context-pressure`；
    用了 `self-estimate` 就如实写。
