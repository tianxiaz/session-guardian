# 触发场景全景（三条失效轴）

> 这份文件是**操作手册**：什么时候必须做交接、用什么词记录、以及为什么有些场景"到点再交接"根本不可能。
> 完整调研与一手证据（Kimi Code 官方 issue 逐字引文、DSH/Claude Code 错误码表、平台信号映射）见
> `docs/77-调研-交接触发场景全景.md`。

---

## 0. 一句话

触发不只"上下文快满了"这一种。共有 **21 个场景**，落在**三条轴**上；其中最危险的一条
（执行中断）**在发生的那一刻模型已经没机会写任何东西**——所以对那条轴，唯一防线是**提前写新**。

---

## 1. 三条轴

| 轴 | 失效方式 | 会话还能继续 | 模型还能动作 | 对策 |
|---|---|---|---|---|
| **A 信息失真** | 上下文被压缩/填满，早期决定失真 | 能 | 能 | **到点交接**（信号来了就写） |
| **B 执行中断** | 会话/请求/进程被外部终止 | 不能 | **不能** | **只能提前写（写前式检查点）** |
| **C 主动边界** | 没出错，只是到了自然交接点 | 能 | 能 | 到点交接 |

---

## 2. A 类：信息失真（6）

| 场景 | 信号 | `trigger` | 动作 |
|---|---|---|---|
| 占用逼近窗口 | 平台量化值越线（按窗口派生，见 `measure`） | `context-pressure` | §4 全流程 |
| 压缩即将发生 | Claude Code/Codex `PreCompact`；Kimi 有事件但返回值被忽略；**DSH 无此钩子** | `pre-compact` | 交接后放行压缩 |
| **压缩刚发生** | `PostCompact`／`SessionStart(compact)`；Kimi 返回值被忽略 | `post-compact` | **重建落地**：重读交接物、重跑验证命令、与仓库实测对齐；**不信摘要** |
| **重复失败不升级**（loop capture） | **自己数**：同一手段连续失败 N 次（建议 N=2） | `degradation` | **熔断**：停下写交接，别继续换皮重试 |
| **指令/角色漂移** | **自查**：本轮产出是否越过 `boundaries.禁止` | `degradation` | 交接 + 重写禁区 |
| 会话中换模型 | `PreModelSwitch`/`PostModelSwitch`；Kimi `/model` | `model-switch` | 交接（新模型不继承隐性上下文） |

> A 类之所以能"到点交接"，只因为**会话还活着**。别把这条当成通用前提。

## 3. B 类：执行中断（10）——**最需要提前准备**

| 场景 | 一手证据（详见 docs/77 §3） | 模型能观测到吗 | `trigger` |
|---|---|---|---|
| 会话假死（请求挂起无响应） | Kimi #3664：长会话 8 个请求全部挂起，`ttft` 达 164 秒，客户端无超时/无提示 | ❌ | 重开后 `interruption` |
| 会话被外部杀死 | Kimi #2622：「session had to be terminated externally. **Goal/task state was lost with the kill**」 | ❌ | 重开后 `interruption` |
| 网络/传输中断 | Kimi #1540「terminate completely」；DSH `TRANSPORT`/`TIMEOUT`/`ABORTED` | ⚠️ 部分 | `error-recovery` |
| 限流/过载/配额/账单 | Claude Code `StopFailure(rate_limit\|overloaded\|billing_error\|account_on_hold)`；DSH `RATE_LIMIT`/`QUOTA` | ✅ | `error-recovery` |
| 撞 max_output_tokens | `StopFailure(max_output_tokens)`；DSH 同名 | ✅ | `error-recovery` |
| 任务超时被强杀 | Kimi #1761：60 秒强杀、不理会模型设的 timeout | ❌ | 重开后 `interruption` |
| 进程崩溃 | DSH `agent/request-error`；Kimi #4128 陈旧锁致会话丢失 | ❌ | 重开后 `interruption` |
| **压缩本身失败** | Kimi #4193：「turn 以 `[compaction.failed]` **硬失败、goal 暂停**」 | ✅ | `compaction-failed` |
| 目标/轮次预算耗尽 | DSH 稳定码 `round-limit`；Kimi `-p` 退出码 3（阻塞）/6（暂停） | ✅ | `round-limit` |
| 会话打不开/锁死 | Kimi #3592：长对话大概率打不开（30 秒超时） | ❌ | 重开后 `interruption` |

### 3.1 三个硬结论

1. **必须"写前式检查点"**：B 类里有 5 个场景模型侧不可观测。发生时你写不了任何东西。
   ⇒ 在**每次真正推进状态之后**就增量刷新交接物（成本很低：只改 1–2 个节）。
2. **不能把交接押在"压缩前"**：B8 证明压缩自己会挂，且挂法是把 turn 打死。
3. **检查点必须便宜**，否则模型一定偷懒。这正是「声明式合并 + 未变节逐字保留」的用处。

### 3.2 必须承认的能力边界（不许含糊成"无损"）

> **本技能无法承诺"一定能接上"。**
> 能承诺的是：**上一个检查点之前的工作可无损接续；检查点之后到中断之间的工作可能丢失。**
> 所以：检查点越勤，可丢失窗口越小。别把"无损"说成全局性质。

## 4. C 类：主动边界（5）——**这里藏着最该优先用的一种**

| 场景 | 信号 | `trigger` |
|---|---|---|
| **一个交付单元完成**（首选） | 见 §4.1 的三条判据 | `phase-complete` |
| 用户明示"交接/换会话" | 对话 | `user-request` |
| 上游/协调方要求 | 多代理编排 | `peer-request` |
| 换设备/换平台继续 | `/fork` 后打印的续接命令；跨设备需求见 kimi #2269 | `device-switch` |
| 例行检查点 | 见 §5 的节奏 | `checkpoint` |

`phase-complete` 与 `checkpoint` 的区别：
- `checkpoint`＝**为了防中断而例行刷新**（可能什么都没交付），粒度为"步"；
- `phase-complete`＝**真的完成了一个可独立验收的交付单元**，粒度为"单元"，且通常要**换会话**。

---

## 4.1 交付单元边界：**质量最高的交接时机**

### 定义（三条同时满足）

1. **有可判真假的验收**：能写出"怎么算完成"；
2. **不依赖未完成的半成品**：接手方不需要先猜你做到哪；
3. **已落盘**：代码已写、已跑过、已（或明确决定不）提交。

典型单元：一个独立功能的设计＋实现、一个 bug 的定位＋修复、一个模块重构、一次数据迁移。
**不是**单元：单个文件改完、单条命令跑通、单个测试变绿 —— 那些只触发**检查点**。

### 为什么它比阈值触发更好（机制层面的理由）

- **交接物质量 ∝ 写它那一刻的自我清晰度。** 单元刚完成时，相关事实都在近期上下文里、无半成品噪音 ⇒ 失真最小。
- **阈值触发落在模型状态最差的时刻。** 长上下文填充后有实测记录的退化（重复循环、不升级、
  指令漂移、盲信压缩摘要，见 §3）——**最需要好交接的时候，产出的交接最差**。
- **单元中途交接天然带半成品**：接续方要先猜进度，"下一步"也碎。

### 单元大小的两侧边界

| 太小（一步一换） | 太大（跨多个单元） |
|---|---|
| 切换开销 > 收益（新会话要重读交接物＋重跑验证） | 交接质量下降、单元间状态纠缠、"下一步"模糊 |

**甜点区＝一个可独立验收的交付单元**。这是经验值，按任务调整。

### 反模式

> **不要在单元**中途**做"完整阶段交接"并换会话。** 中途只做轻量检查点（防中断）；
> 等单元完成再做阶段交接。中途硬换会话，效果通常比不换更差。

### 证据强度（如实）

这一节来自**用户实操观察**（2026-10-17，在 Kimi 上做大型项目）："完成一组独立任务后触发会话切换，
既不会因为中断续接影响任务完成效果，会话切换的效果也比较完整。"
**n 小、无对照实验、由使用者自评**——所以它是**有机制解释的经验规律**，不是受控实验结论。
按它做不会更差；但别把它当成"已验证的最优策略"。

## 4.2 下一单元探测：三种"界定边界"的方案与取舍

用户提出的三种做法（2026-10-17），逐条评估：

| # | 方案 | 优点 | 缺点 | 采纳 |
|---|---|---|---|---|
| 1 | **用户主动要求** | 最准：人有 Agent 看不到的全局（项目节奏、deadline、精力、是否要开会） | 靠人记得；人**看不到** Agent 的内部状态，反而常在"已经乱了"时才想起来 | ✅ 保留为最强入口（`user-request`），但不能当唯一机制 |
| 2 | **Agent 界定 → 提示用户 → 用户决定** | 信息与权威各归其位：Agent 知道自己刚做了什么，用户知道该不该现在切 | 需要不烦人的提议 + 用户能一句话决策 | ✅ **主方案** |
| 3 | **探测到"下一步是新任务"就中止、切换、告知** | 把边界变成**可判定的问题**（"下一步是否同一件事"比"我做完了吗"锐利得多） | **"自动中止"危险**：判错会打断正常流程；且 Agent 无法自己结束会话 | ✅ 采纳其**探测信号**，**不采纳其"自动中止"** |

⇒ **最终设计＝方案 3 的探测信号 + 方案 2 的控制权 + 方案 1 的显式入口。**

### 为什么"下一步是否同一件事"比"我做完了吗"更好用

"我做完了吗"要求 Agent 对整体有判断，容易自我抬高（默认倾向是"再多做点"）。
"下一步是不是同一件事"只要求比较**两个相邻动作**，判据更硬，也更接近边界的定义。

### 判别四信号（本体 §1.2 有同表）

验收标准 ／ 改动面 ／ 依赖关系 ／ 交付状态。四条里三条指向"新"，就按新单元处理。

### 探测必须在**动作之前**

等已经开始新单元再探测，上下文已被污染——那时换会话也救不回"上一单元最清晰"的优势。

### 三条硬约束

1. **不自动中止**：Agent 结束不了会话，只能停止推进 + 交回决定权。写成"已中止"＝声称未做之事。
2. **不阻塞**：提议被无视后照常继续，不重复唠叨。
3. **不以占用率为由提议**：依据必须是单元边界。占用低也可能该换（单元刚收尾），
   占用高也可能不该换（只差最后一步）。

### 已知失效模式

- **误判为边界**：一个功能开发到一半，觉得"下一步写文档＝新任务"，其实文档是同一单元的一部分。⇒ 用"交付状态"这条压住。
- **漏判**：跨模块重构一路"还是同一件事"，很晚才意识到边界。⇒ 配合 §5 的检查点节奏兜底。
- **提示疲劳**：每个单元都提。⇒ 人说过"继续"之后短时内不再提。

## 5. 检查点节奏（B 类唯一防线的操作规则）

**什么时候写检查点**（满足任一）：

1. 一个**可验证**的步骤刚完成（测试转绿、文件落盘、命令跑通）；
2. `boundaries.禁止` 或 `status.下一步` 发生变化；
3. 距上次检查点已经过了**若干轮**（建议 5–10 轮，视每轮信息量调）；
4. 你准备进入一段**长耗时**操作（大重构、批量跑测试、长命令）——**动手之前**先写；
5. 你怀疑自己开始"重复同一手段"（`degradation` 前兆）——立即写。

**怎么写才便宜**：

```bash
# 只声明变化的那 1–2 个节；其余由工具逐字搬运
node "<技能目录>/scripts/check_handoff.mjs" next ./HANDOFF.md --payload p.json --archive-dir .handoff-archive
```

```json
{ "changed": ["status"], "sections": { "status": "- 已完成：…\n- 进行中：…\n- 阻塞：无\n- 待办：…\n- 下一步：…\n- 验证：…\n- 恢复检查点：HEAD=<哈希>" } }
```

**检查点的判据与完整交接完全相同**（`check` 必须判绿）。唯一区别是**频率**，不是质量。

### 5.1 实测成本（2026-10-16，本机实测，非估算）

| 场景 | 耗时 | 未变节逐字保留 | 文件字节变化 |
|---|---|---|---|
| 单节检查点（只改 1 个节） | **约 170 ms** | **7/8 节字节完全相同** | +32 B（只有那 1 节变） |
| 两节检查点（改"待办"） | **约 160 ms** | 只有声明的节变 | 同上量级 |

**一个必须知道的工效成本**：改 `status.待办` **必须同时声明 `todo`**（两处副本逐字节一致，判据会拦）。
所以"改待办"这类检查点要写 2 个节，不是 1 个。这不是缺陷，是设计（防两处漂移）。

⇒ 结论：一次检查点约 **0.2 秒**、只改动几十字节。**没有任何理由为了省这点成本而不写**。

## 6. 触发词 → 动作 速查

| `trigger` | 是否要求"必须交接" | 附加动作 |
|---|---|---|
| `context-pressure`（旧别名 `external-threshold`） | 是 | 记录 occupancy |
| `pre-compact` | 是 | 交接后才放行压缩；**不允许只阻断不交接** |
| `post-compact` | 是 | **重建落地**：重读交接物＋重跑验证命令，把摘要里的"已完成"当未验证 |
| `degradation` | 是 | 在 `decisions.尝试过` 里写清"试过什么、为什么不行"，避免下一个人重走 |
| `error-recovery` / `compaction-failed` / `round-limit` / `budget-quota` | 是 | `trigger_detail` 写平台稳定码 |
| `model-switch` | 是 | 新模型不继承隐性上下文，交接后让它先重建落地 |
| `interruption` | 是（重开后第一件事） | 先核对 `status.恢复检查点`，再继续 |
| `checkpoint` | 是（例行） | 只改变化节，保持便宜 |
| `phase-complete` | 是 | 通常需要同时更新 `evidence` |
| `user-request` / `peer-request` / `device-switch` | 是 | 按用户/上游要求 |
| `self-estimate` | 是 | **必须如实标注**，不许伪装成外部阈值（判据会拦） |

## 7. 与各平台的关系

**能力矩阵**（哪些信号能自动拿）见 `references/platforms.md`。这里只强调三条：

- **DSH**：有 `contextPressure` 量化与 `RATE_LIMIT`/`QUOTA`/`TRANSPORT`/`TIMEOUT` 稳定码，
  但**没有压缩前钩子** ⇒ `pre-compact` 拿不到，只能靠 `context-pressure` + `checkpoint`。
- **Claude Code**：信号最全（`PreCompact`/`PostCompact`/`StopFailure` 12 种错误/`PreModelSwitch`），
  但**没有官方占用百分比** ⇒ `context-pressure` 要用派生阈值或 transcript 近似。
- **Kimi**：`PreCompact`/`PostCompact` 存在但**返回值被忽略**（不能阻断、不能注入）；
  `SessionStart` 不能注入上下文 ⇒ 想自动提醒只能挂 `UserPromptSubmit`。
  `/usage` 有占用与配额；`-p` 退出码 3/6 可作 `round-limit` 信号。
- **所有平台共同**：B 类里的假死/被杀/超时/崩溃**都不可观测** ⇒ `checkpoint` 是唯一的通用答案。
