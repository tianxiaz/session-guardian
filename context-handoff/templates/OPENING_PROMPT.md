# 新会话开场指令（直接复制粘贴这一段）

> 生成规则：`<交接物路径>` 换成真实路径；`<下一步>` 抄 `HANDOFF.md` 的 `status.下一步` **原文**；
> `<验证命令>` 抄 `environment.命令` 里真跑过的验证命令。
> **只写这三件事**：读哪个文件、按哪一节执行、铁律一句话。不要复述交接物内容（那会让新会话
> 依赖这份指令而不是依赖交接物，交接物一改就漂移）。

```
接手一个进行中的任务，先读 <交接物路径>（接续必需信息全在里面；里面的「状态/下一步」就是要你做的第一件事）。

执行要求：
1. **先重建落地，别急着干**。跑 <验证命令>，并把 `git rev-parse HEAD` 与交接物里的
   `status.恢复检查点` 对比，确认仓库/工作区状态与交接物描述一致；不一致就以实测为准并先纠正交接物
   （这是"五问"的第 5 问）。
   ⚠️ **把交接物里所有"已完成"当"未验证"**：一条条用实测确认，不要因为写着完成就跳过。
   （若上一次会话是被压缩/被中断结束的，摘要与交接物都可能带着没核实的"已完成"。）
2. 按 HANDOFF 的 status.下一步 执行 <下一步>。
3. 严格遵守 boundaries.禁止（尤其：不要动别人未提交的在建文件；不要 git add -A）。
4. 铁律：判据不放宽；变异必须能红；空面必须判红；引用文件行号前回读原文；不许声称未做之事；
   未完成项逐条如实列出。
5. **按"检查点"节奏维护交接物**（不是等上下文吃紧才写）：每完成一个可验证步骤、或改动
   boundaries/下一步、或准备进入长耗时操作**之前**，就用 context-handoff 做一次**增量**交接
   （只声明变化的 1–2 个节，未变节逐字保留）。
   原因：假死/被 kill/超时/崩溃发生时你已经没机会写了——**上一个检查点之后的工作可能丢，
   之前的一定能接上**。
6. 若怀疑自己在重复同一手段，就在 `decisions.尝试过` 里写清"试过什么、为什么不行"，
   然后停下交接，别继续换皮重试。
```

## 若对方**读不到**本机文件系统（纯对话型平台：网页版对话框等）

上面的指令会失效——对方第一步"去读某个路径"就走不动。此时改用**自包含形态**：
把交接物的**正文全文**贴在指令后面，并把第一句改成"以下是你需要的全部背景"。

```
以下是你需要的全部背景（不需要读任何外部文件）。请按其中的「状态/下一步」继续，
并严格遵守「边界与禁区」。

===== HANDOFF 全文开始 =====
<把 HANDOFF.md 全文粘贴在这里>
===== HANDOFF 全文结束 =====

铁律：判据不放宽；变异必须能红；空面必须判红；不许声称未做之事；未完成项逐条如实列出。
另外：把上面的「已完成」逐条当**未验证**核对；每完成一个可验证步骤就让我把最新交接物再贴一份给你
（自包含形态下你改不动我的文件，只能我这边落盘）。
```

**注意自包含形态的代价**：粘贴过去的是**快照**，对方改不动原文件，下次交接会出现两份互相
矛盾的副本。所以只把它当"降级档 C"，能读文件系统时一律用上面的路径形态。

## 附：新会话验收标准是「五问」

新会话**仅凭交接物**必须能答出：① 目标与验收 ② 下一步 ③ 禁区 ④ 验证命令 ⑤ 基线与当前仓库是否一致。
第 ⑤ 问**不能**由交接物单独回答（它只负责给出基线与判断方法），需要新会话自己跑 `git rev-parse HEAD` 比对。
`check` 机械兜底前四问的字段完整性；第 ⑤ 问靠 `status.恢复检查点` 存在 + 新会话实际比对。
